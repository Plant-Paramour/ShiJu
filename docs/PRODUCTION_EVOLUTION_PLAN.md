# 诗矩生产化演进方案

本文档面向从 MVP 进入公网生产环境的阶段，重点解决以下问题：

- 几百名用户同时访问和使用 Agent 时，API 不被长时间模型请求拖垮；
- 支持多个 OpenAI-compatible 服务商、URL、Key 和 Model；
- 某个端点限流、超时或故障时，自动切换到其他端点；
- 主力模型不可用时，使用稳定的备用和兜底服务；
- SQLite 平滑迁移到 PostgreSQL；
- 在有限服务器预算下，优先保证用户体验和服务可靠性。

当前 `docs/DISTRIBUTED_ARCHITECTURE.md` 描述的是 MVP 的“常驻控制面 + 按需 GPU Worker”方案。本文件是面向正式生产环境的后续演进方案。两者的业务边界保持一致，但生产环境不再以 `2核2G + SQLite` 作为长期容量目标。

## 1. 总体决策

### 1.1 保留 Python 和 FastAPI

不因为并发预期而重写为 PHP。当前主要耗时来自：

- 上游大模型请求；
- Agent 工具调用轮次；
- GPU 冷启动和生成；
- 数据库事务和事件写入；
- SSE 长连接和任务排队。

这些问题不会因为更换为普通 PHP-FPM 而自动消失。Python 仍然适合 API、Agent 编排、任务控制和 GPU Worker。真正需要改进的是并发模型、数据库和外部模型调用层。

### 1.2 正式环境使用 PostgreSQL

SQLite 继续用于本地快速测试或单机开发，但正式公网环境迁移到 PostgreSQL。迁移完成后，不再把 SQLite 作为生产主数据库。

PostgreSQL 主要解决：

- 多个 API 进程并发写入；
- 用户、会话、消息、论坛和任务数据的事务一致性；
- 任务领取和事件追加的行级锁；
- 数据库备份、恢复和监控；
- 后续增加应用实例时的共享状态问题。

PostgreSQL 不能消除所有数据库瓶颈，仍然需要短事务、索引、分页、连接池和事件保留策略。

### 1.3 增加模型网关层

Agent 不再直接持有单个 `base_url + api_key + model` 配置，而是统一调用模型网关：

```text
浏览器
  -> FastAPI 控制面
  -> Agent 执行器
  -> Model Gateway
  -> 主力、备用、兜底模型端点池
```

模型网关负责端点选择、并发限制、超时、错误分类、熔断、重试、故障切换和调用记录。Agent 只关心标准化后的模型响应和工具调用。

## 2. 服务器预算评估

### 2.1 `4核8G、5M、180G系统盘、500G/月`

这个配置可以作为第一版正式应用服务器，前提是数据库独立部署或使用托管 PostgreSQL，且静态资源和大文件不全部从这台机器提供。

它适合：

- FastAPI、反向代理和用户业务 API；
- Agent 请求接入和有限并发的 Agent 执行器；
- 论坛、词典、韵书、词牌查询；
- SSE 状态推送；
- GPU 任务提交、查询和结果展示；
- 几百名在线用户，以及其中一部分同时进行 Agent 对话。

它不应被理解为可以让几百个 Agent 请求同时无限制地调用大模型。真正的并发上限还取决于上游服务商额度、端点并发限制、模型响应时间和数据库负载。

如果把 PostgreSQL 也放在同一台机器上，4核8G仍可用于早期生产，但应用进程、数据库和日志会竞争内存。此时应减少应用进程数量，限制数据库连接，并做好备份；更推荐使用独立或托管 PostgreSQL。

180G系统盘足够放置应用、依赖、日志轮转和少量备份，但不应放模型权重、用户图片或论坛附件。模型权重放在 GPU 服务器，用户上传内容放对象存储。

### 2.2 5M 与 12M 带宽

5M 带宽的理论峰值约为 625KB/s。对于纯文字 JSON、Agent 事件和任务状态，它通常够用；500G/月也不是主要问题，真正的限制是瞬时峰值带宽。

如果满足以下条件，5M 可以先上线：

- 页面静态文件使用 CDN 或缓存；
- 头像、图片和附件使用对象存储；
- API 主要传输文字和小型 JSON；
- 不从应用服务器提供模型文件和大文件下载。

如果 12M 的价格差距可以承受，生产环境可以直接选择 12M。它会改善首次打开网页、图片访问、多人同时加载静态资源时的体验，但它不能替代 PostgreSQL、缓存、限流和 Agent 并发控制。

预算有限时，优先级建议为：

```text
数据库可靠性和备份 > 内存容量 > CPU > 带宽升级
```

如果数据库已经独立，且静态资源已经 CDN 化，那么 5M 可以先运行；如果没有 CDN、论坛包含图片、或者 12M 只增加少量成本，则建议购买 12M。

### 2.3 建议的第一版生产部署

```text
应用服务器：4核8G，5M至12M，180G系统盘
数据库：托管 PostgreSQL，至少 2核4G，建议自动备份
GPU服务器：T4，按需开机，运行独立 Worker
对象存储：头像、图片、附件和导出文件
反向代理：Nginx 或 Caddy，负责 HTTPS、压缩和静态缓存
```

如果只能购买两台机器，应把数据库视为独立的逻辑资源，优先购买托管 PostgreSQL，而不是把数据库和 API 长期混在一起。

## 3. Agent 并发模型

### 3.1 当前实现的限制

当前 Agent 客户端使用同步 HTTP 请求，Web Agent 路由也存在同步执行路径。一个请求等待上游模型时，会占用一个同步线程。当前 API 启动配置还是单 Uvicorn Worker，Web Agent 会话也有进程内存状态。

因此，当前实现适合本地联调和小规模内测，但不能直接承诺几百个同时进行的 Agent 请求。

### 3.2 目标执行流程

```text
用户发送消息
  -> API 鉴权、限流、创建 Agent turn
  -> Agent 执行器接收任务
  -> 模型网关选择端点
  -> 调用模型并执行工具循环
  -> 持久化事件和最终结果
  -> SSE 或查询接口返回状态
```

普通 API 不应长时间等待模型完成。Agent 请求需要有明确的执行并发上限，超过上限的请求进入短队列或快速提示繁忙。

### 3.3 并发控制

至少设置三层限制：

- 全局 Agent 并发上限；
- 每个服务商或端点的并发上限；
- 每个用户的并发和每日额度。

例如第一版可以先控制为全局几十个进行中的模型请求，具体数值由上游配额和压测决定，不直接以在线用户数量作为模型并发数。

SSE 连接应采用异步方式或独立事件推送机制，不能让每个等待中的连接长期占用普通同步线程。

## 4. 模型端点池

### 4.1 端点配置

每个可用端点应具有以下属性：

| 属性 | 含义 |
| --- | --- |
| `provider_id` | 服务商标识 |
| `base_url` | OpenAI-compatible 服务地址 |
| `model` | 模型名称 |
| `secret_ref` | Key 的安全引用，不保存明文到代码 |
| `tier` | `primary`、`secondary` 或 `emergency` |
| `priority` | 端点优先级 |
| `weight` | 同级端点的选择权重 |
| `max_concurrency` | 端点并发上限 |
| `timeout_seconds` | 请求超时时间 |
| `supports_tools` | 是否支持 Agent 工具调用 |
| `supports_stream` | 是否支持流式返回 |
| `cost_level` | 成本等级 |

URL、Key 和 Model 必须作为一个完整端点组合管理，不能只轮换 Key 而忽略对应模型和服务商能力差异。

### 4.2 分层策略

`primary` 主力池：日常使用的低成本、低延迟端点，可以配置多个服务商和多个合法配额 Key。

`secondary` 备用池：主力池限流、延迟过高或局部故障时使用，优先选择兼容性好的模型。

`emergency` 兜底池：购买稳定服务并单独保留额度，只在前两层无法使用时启用。兜底端点也必须支持工具调用，否则只能作为普通聊天的有限降级方案。

### 4.3 选择策略

每次请求按以下顺序选择：

1. 过滤不支持当前功能的端点；
2. 排除熔断、冷却或达到并发上限的端点；
3. 优先选择主力池；
4. 在同一层根据优先级、权重、当前并发和近期延迟选择；
5. 失败后尝试同层其他端点；
6. 最后进入备用池和兜底池。

不能使用无条件的简单轮询。轮询会把请求继续分配给已经限流或持续失败的端点。

## 5. 故障切换规则

### 5.1 错误分类

| 错误 | 处理方式 |
| --- | --- |
| 401、403 | 暂时禁用对应 Key，告警并等待人工检查 |
| 429 | 读取冷却时间，端点暂时降权或熔断 |
| 连接失败、超时 | 有限重试并切换端点 |
| 500、502、503、504 | 有限重试并切换端点 |
| 400、模型不存在、参数不支持 | 不重复请求同一端点，记录兼容性问题 |
| 内容审核拒绝 | 不通过换服务商无限重试 |
| 工具调用格式非法 | 降低端点评分，必要时暂时停用 |

单个用户请求最多尝试有限数量的端点。不能无限重试，否则会增加费用、延迟和重复工具调用风险。

### 5.2 熔断

端点需要维护：

- 最近失败次数；
- 最近成功率；
- P50、P95 延迟；
- 当前并发数；
- 最近一次 429 或 5xx 时间；
- 熔断结束时间。

连续失败后进入熔断状态，冷却一段时间后使用少量探测请求恢复。健康状态不能只看服务商的 `/models` 接口，真实请求的成功率更有参考价值。

### 5.3 流式响应的特殊规则

在首个 token 发出前失败，可以透明切换到其他端点。

已经向用户发出部分文本后再失败，不能假装无缝切换，否则可能产生重复文本。此时应记录中断事件，由前端显示“响应中断，可重试”，或者启动一次明确的重新生成。

模型已经返回工具调用并执行工具后，后续模型请求失败时，备用模型必须接收完整的消息和工具结果。生成任务仍然必须使用幂等键，避免重试造成重复 GPU 任务。

## 6. 安全和成本控制

- Key 只通过环境变量、密钥管理服务或加密配置提供；
- 日志只能记录 `provider_id`、`model`、请求 ID 和错误分类，不能记录 Key；
- 不记录完整用户隐私内容和完整 Authorization 请求头；
- 为每个服务商设置每日预算和请求额度；
- 为每个用户设置并发限制、每日调用额度和单次超时；
- 兜底服务必须预留真实可用额度，不能只配置一个没有余额的 URL；
- 多个 Key 只有在服务商明确允许并且确实拥有对应配额时才加入池中。

模型池不是无限扩容手段。多个 Key 如果共享同一个账户或上游配额，仍然会受到同一个服务商的总限制。

## 7. 数据库和状态改造

### 7.1 PostgreSQL

迁移 PostgreSQL 时保留现有 Repository 层的业务接口，避免同时重写业务逻辑。需要单独处理：

- 连接池；
- PostgreSQL migration；
- 参数占位符和时间类型；
- 事务边界；
- 任务领取锁；
- Agent 事件追加；
- 高频查询索引和分页；
- 事件表归档和保留期限。

一次 Agent turn 中的消息、turn、关键事件和提案更新应设计清晰的事务边界，避免每个小步骤都单独打开连接并提交。

### 7.2 会话状态

正式环境不能只依赖 `WebAgentService` 的进程内会话字典。用户会话、消息、待确认提案和任务上下文应以数据库为准。

进程内可以保留短期缓存，但 API 重启、多个 Worker 或多台应用服务器不能导致会话丢失或状态分叉。

### 7.3 Redis 的引入时机

第一阶段可以先使用 PostgreSQL 和独立 Agent 执行器，不强制引入 Redis。

出现以下情况后再引入 Redis：

- 多个 Agent Worker 需要共享并发计数；
- 多个 API 实例需要共享限流和熔断状态；
- SSE 事件推送不适合继续轮询数据库；
- 需要短期缓存词典、词牌和热门论坛数据。

## 8. 分阶段实施顺序

### 阶段一：生产基础

- 应用服务器升级到 4核8G；
- 部署 HTTPS、反向代理和日志轮转；
- PostgreSQL 完成迁移和自动备份；
- Agent 会话、消息和提案以数据库为准；
- 增加用户鉴权、限流和调用额度；
- 继续保持 GPU Worker 独立。

### 阶段二：模型网关

- 将单一模型客户端抽象为模型网关；
- 支持多个 URL、Key、Model 端点；
- 增加端点能力声明和兼容性校验；
- 增加并发上限、超时、错误分类和有限重试；
- 记录端点、模型、耗时、状态码和失败原因。

### 阶段三：可靠性

- 加入熔断、冷却和备用池；
- 配置独立的稳定兜底服务；
- 为工具调用和生成任务增加重试幂等验证；
- Agent 执行器与 Web API 进程分离；
- 统一处理排队、取消和超时。

### 阶段四：按压测结果扩展

- 根据数据库锁等待和连接池使用率决定是否扩容数据库；
- 根据 API P95 延迟决定是否增加应用 Worker 或应用服务器；
- 根据 SSE 连接数和事件读取压力决定是否引入 Redis；
- 根据 GPU 队列长度决定是否增加 GPU 实例；
- 根据模型服务商的实际限流决定是否扩大合法端点池。

## 9. 上线验收指标

正式扩大用户范围前，至少需要测量：

- 普通 API 的 P50、P95、P99 延迟；
- Agent 首个事件和最终响应延迟；
- 不同端点的成功率、429 比例和超时比例；
- Agent 每次请求平均模型调用轮数；
- 数据库连接池等待时间；
- 数据库锁等待和慢查询；
- SSE 同时连接数；
- 生成任务排队长度和 GPU 冷启动时间；
- 应用内存、CPU、磁盘和带宽峰值。

需要用真实或脱敏的生产形态数据做压测，不能只依据服务器配置表判断“能承受多少用户”。

## 10. 最终建议

当前预算下，推荐直接采用：

```text
4核8G应用服务器
12M带宽（如果价格差距不大）
托管 PostgreSQL
对象存储和 CDN
T4 按需 GPU Worker
多端点 Model Gateway
主力池 + 备用池 + 兜底池
```

如果 12M 明显增加成本，5M 也可以先上线，前提是静态资源、图片和附件不依赖应用服务器直出。相比从 5M 升级到 12M，更应该优先保证数据库备份、连接稳定性、模型兜底额度和 Agent 限流机制。
